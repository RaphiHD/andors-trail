# Maps & The World

## Overview

Andor's Trail's game world is a set of fixed, hand-authored maps (`PredefinedMap`), each backed by a [Tiled](https://www.mapeditor.org/) `.tmx` file bundled as an Android XML resource. Each map is a small grid of tiles arranged in five fixed rendering layers, plus a set of rectangular "map objects" (signs, map-change exits, rest spots, key-gated areas, containers, scripted trigger areas) parsed out of the TMX object groups. Players move between maps through `newmap`-type map objects rather than one continuous scrollable world; a separate, much lower-resolution **world map** is stitched together from rendered screenshots of each visited map and is shown to the player as an HTML page for orientation/fast-travel context (it is a picture, not a playable map). Some maps can also change their own layout at runtime — a "replaceable map section" swaps a rectangular block of tiles for an alternate one when a quest/script requirement becomes true (e.g. a bridge appearing, a door opening).

## How it works

### Map data model: layers, tiles, sections, objects

A `PredefinedMap` has a fixed `Size` (width/height in tiles) and owns one `LayeredTileMap`. The `LayeredTileMap.currentLayout` is a `MapSection`, which bundles exactly five `MapLayer`s in fixed paint order — `layerBase`, `layerGround`, `layerObjects`, `layerAbove`, `layerTop` — each a `int[width][height]` grid of tile IDs (`MapLayer.tiles`), plus a `boolean[width][height] isWalkable` grid and an MD5 `layoutHash`. `LayeredTileMap.isWalkable(Coord/CoordRect)` is the map's ground-truth walkability check (bounds-checked via `isOutside`), used directly by `PredefinedMap.isWalkable(...)` and indirectly by pathfinding (see [movement-pathfinding.md](./movement-pathfinding.md)).

Separately from the tile layers, each map has a flat `MapObject[] eventObjects` array — rectangular, typed trigger areas that are *not* rendered as tiles but overlay the map. `MapObject.MapObjectType` is one of:

- `sign` — shows/runs a text phrase (`worldEventListeners.onPlayerSteppedOnMapSignArea` + `runScriptInArea`).
- `newmap` — a map-change/exit trigger; carries the destination `map` name and `place` name.
- `rest` — a resting spot; sets the player's respawn point.
- `keyarea` — gated by a `Requirement`; blocks movement/triggers a script until satisfied.
- `container` — a lootable container tied to a `DropList`.
- `script` — runs a conversation-engine script phrase; can be evaluated `whenEntering`, `onEveryStep`, `afterEveryRound`, or `continuously` (`MapObjectEvaluationType`).

Each `MapObject` also carries a `group` string used for bulk activation (`PredefinedMap.activateMapObjectGroup`/`deactivateMapObjectGroup`, called by `MapController`), and an `isActive` flag — inactive objects are invisible to `getActiveEventObjectsAt`/`findEventObject`, so a whole group of signs/exits/containers can be turned on or off at once (e.g. by a quest script) without editing map data.

`MonsterSpawnArea` and `TravelDestinationArea` are kept in their own arrays on `PredefinedMap` (`spawnAreas`, `destinationAreas`) rather than in `eventObjects`, since they are not "stepped-on" triggers in the same sense; both extend the common `MapArea` base (`area`, `areaID`, `mapID`). `PredefinedMap.getArea(areaID)` looks up either kind by ID.

### Loading maps from TMX

Map loading is split into two layers:

1. **`TMXMapFileParser`** is a pure XML/format reader. It knows the Tiled TMX schema (map/tileset/layer/objectgroup/object/property) and Tiled's tile-layer encoding (base64 text, optionally zlib- or gzip-compressed, 4 bytes little-endian per tile GID — `readTMXMapLayerData`), but has zero game semantics. It hard-codes an expected tile size of 32px (`TILESIZE`) and logs a warning (under `DEVELOPMENT_VALIDATEDATA`) if a map's declared `tilewidth`/`tileheight` disagrees. It also computes an MD5 hash per raw tile layer (`TMXLayer.layoutHash`) from the decoded GID buffer. There are two parse entry points: `readObjectMap` (objects/properties only, used for the world/name-resolution pass) and `readLayerMap` (full layers + tilesets + objects, used to actually build a `LayeredTileMap`).
2. **`TMXMapTranslator`** turns those raw DTOs into game model objects:
   - `transformMaps(...)` iterates every parsed `TMXObjectMap`'s `objectgroup`s and, per `<object>`, dispatches on `object.type` (`sign`, `mapchange`, `spawn`, `destination`, `key`, `rest`, `container`, `replace`, `script`) to build the corresponding `MapObject`/`MonsterSpawnArea`/`TravelDestinationArea`. Object pixel coordinates are converted to tile coordinates by `getTMXObjectPosition` (divides by `tilewidth`/`tileheight` and rounds). A `TMXObjectGroup`'s own `active` property seeds `PredefinedMap.initiallyActiveMapObjectGroups`. `spawn` objects resolve a `spawngroup` property to a set of `MonsterType`s via `monsterTypes.getMonsterTypesFromSpawnGroup`; if none resolve, the spawn is silently dropped (only logged under `DEVELOPMENT_VALIDATEDATA`). Map-level properties `outdoors` and `colorfilter` become `PredefinedMap.isOutdoors`/`initialColorFilter`.
   - `transformMap(...)` builds the `LayeredTileMap`: it reads a fixed set of layer *names* — `base`, `ground`, `objects`, `above`, `top`, `walkable` (case-insensitive, matched by string, see `LAYERNAME_*`/`defaultLayerNames`) — to build the default `MapSection`, and separately walks `replace`-typed TMX objects to build each `ReplaceableMapSection` (each `replace` object can point at a *different* set of named layers via `base`/`ground`/`objects`/`above`/`top`/`walkable` properties, letting a replacement section pull tiles from alternate named layers drawn elsewhere in the same TMX file). The `walkable` layer is inverted into `isWalkable`: any non-zero tile GID makes that cell non-walkable (`transformWalkableMapLayer`); a cell with no tile on the walkable layer defaults to walkable.
   - Each tile's `(tilesetName, localId)` is resolved from its numeric GID against the map's `TMXTileSet[]` (`getTile`, matching the highest `firstgid <= gid`), then mapped to an engine-wide integer tile ID via `TileCache.getTileID`, and collected into `LayeredTileMap.usedTileIDs` (used elsewhere to know which bitmap tiles a map needs cached in memory).
   - `readLayeredTileMap(Resources, TileCache, PredefinedMap)` is the static entry point used whenever a map's tiles need to be (re)loaded — both for the currently-entered map (`MovementController.prepareMapAsCurrentMap`) and, separately, when only a screenshot is needed for the world map (`WorldMapController.populateWorldMap`).
   - A `replace` object's `Requirement` is parsed from its TMX properties (`requireType`/`requireId`/`requireValue`/`requireNegation`), and if that fails to parse, `TMXMapTranslator` falls back to interpreting the object's *name* as a quest-progress shorthand (`QuestProgress.parseQuestProgress`); if neither parses, the replacement is dropped entirely with a validation warning.

### Map transitions (`newmap` exits)

Stepping onto a `newmap`-type `MapObject` is handled in `MapController.handleMapEvent`: it computes the player's offset within the trigger rectangle (`offset_x`/`offset_y`, so entering a wide door at a different point lands you at the correspondingly offset point on the other side), migrates any monster mid-travel (`travelDestination != null`) off the current map into `world.monsters`' travelling pool, and calls `MovementController.placePlayerAsyncAt(MapObjectType.newmap, o.map, o.place, offset_x, offset_y)`.

`placePlayerAsyncAt` runs the transition on a background `AsyncTask` (pausing/resuming `GameRoundController` around it) and calls `placePlayerAt`, which:

1. Looks up the destination `PredefinedMap` by name (`world.maps.findPredefinedMap(mapName)`) and the destination `MapObject` by type+name on that map (`newMap.findEventObject(objectType, placeName)`) — an inactive destination place is rejected.
2. Sets `player.position`/`lastPosition` to the destination place's top-left plus the clamped offset.
3. If the destination map has never been visited, runs `playerVisitsMapFirstTime` (creates all container loot up front, marks the world map dirty).
4. Calls `prepareMapAsCurrentMap(newMap, res, true)`, which reloads the destination's `LayeredTileMap`/tiles from TMX (`TMXMapTranslator.readLayeredTileMap`), pre-caches tiles for maps adjacent to it (`world.tileManager.cacheAdjacentMaps`), replaces `world.model.currentMaps` with a new `MapBundle`, applies any due `ReplaceableMapSection`s, spawns monsters (unless the map `isRecentlyVisited()`), re-primes the map script executor (`prepareScriptsOnCurrentMap`), marks the map `visited`/updates its last-visit time, and refreshes the world-map screenshot for the new current map.

The same `placePlayerAsyncAt` path (with `MapObjectType.rest`) is used for player respawn after death (`respawnPlayerAsync`, using the player's stored spawn map/place from `rest`-area interactions — see `MapController.rest`).

`PredefinedMap.calculateDistanceMatrix` (run once in the `PredefinedMap` constructor) pathfinds between every pair of `newmap` exits on that single map and caches the tile distances (`mapchangeDistances`/`mapchangeIndices`, queried via `getDistance`/`setDistance`) — this is an in-map "how far apart are these two exits" table, not a between-maps route planner.

### The world map (overworld)

There is no single scrollable overworld map object in this codebase — the "world map" the player sees is a generated HTML page assembled from small bitmap screenshots of every map the player has already visited, grouped into named `WorldMapSegment`s (`MapCollection.worldMapSegments`, keyed by segment name; `getWorldMapSegmentNameForMap` finds which segment a given map belongs to).

- **Per-map screenshot**: `WorldMapController.updateWorldMap` (called after every map transition and after any layout-changing replacement) checks `shouldUpdateWorldMap` — regenerate if forced (`world.maps.worldMapRequiresUpdate`), if the map has never been visited before, or if the cached PNG/combined HTML file is missing. If needed, a background `AsyncTask` renders the map's current tile layout at a fixed low resolution (`WORLDMAP_SCREENSHOT_TILESIZE = 8` px/tile, vs. the normal 32px tile size) by drawing all five layers in order (`MapRenderer.drawMap`) and writes it as a PNG named after the map (and, once the map has been seen, suffixed with its current `lastSeenLayoutHash` so a post-replacement layout gets a distinct cached image — see Gotchas).
- **Segment assembly**: `updateWorldMapSegment`/`getWorldMapSegmentAsHtml` positions each visited map's PNG as an absolutely-positioned `<img>` inside an HTML template (`R.string.worldmap_template`), using each `WorldMapSegmentMap.worldPosition` (in tile units, scaled by `WORLDMAP_DISPLAY_TILESIZE`) offset so the segment's bounding box starts at the origin. `NamedWorldMapArea`s (settlements etc.) are drawn as labeled `<div>`s spanning the bounding box of their member maps. The resulting HTML file is written per-segment (`getCombinedWorldMapFile`) and displayed by `DisplayWorldMapActivity` when the player opens the world map (`WorldMapController.displayWorldMap`, which no-ops with a toast if the current map has no segment).
- **First-run backfill**: `populateWorldMap` (called once per savegame via a per-player marker file) walks every already-visited map at load time and (re)builds any missing screenshot/segment HTML, loading tiles on demand via `TMXMapTranslator.readLayeredTileMap` if needed — this is how a loaded savegame gets a world map without having to physically re-enter every map.

In short: "fast travel" in this codebase is really "walking through `newmap` exits map by map," and the world map is a *visual reference/progress map*, not a travel-selection UI with its own transition logic — no code path here jumps the player directly to an arbitrary point on the world map.

### Replaceable map sections (quest-driven layout changes)

A `ReplaceableMapSection` (built at TMX-load time from a `replace`-typed TMX object, see above) pairs an alternate `MapSection` with a `replacementArea` `CoordRect` and a `Requirement`. All of a map's replacements live in `LayeredTileMap.replacements`.

Application happens in `MapController.applyReplacements(map, tileMap)`, called from `applyCurrentMapReplacements` (itself invoked after any script runs — `runScriptInArea`/`TravelDestinationArea.onMonsterArrived` — and after `prepareMapAsCurrentMap`/`lotsOfTimePassed`):

1. For every not-yet-`isApplied` replacement whose `Requirement` is currently satisfied (`MapController.satisfiesCondition` → `ConversationController.canFulfillRequirement`), the requirement's fulfillment side effects run (`ConversationController.requirementFulfilled`), and `tileMap.applyReplacement(replacement)` overwrites the target rectangle in the map's default `MapSection` with the replacement's layers/walkability (`MapSection.replaceLayerContentsWith`) and XORs the section's layout hash.
2. Because replacements can overlap, applying one can silently undo the visible effect of another: any other *already-applied* replacement whose area intersects the one just applied has its `isApplied` flag reset to `false` so it will be reconsidered (and potentially reapplied) the next time replacements are evaluated.
3. If the map has a `currentColorFilter` set (independent of tile replacement) that differs from the tile map's live filter, `tileMap.changeColorFilter(...)` is applied and also counts as an "update."
4. Any change (a replacement applied or the color filter changed) marks `world.maps.worldMapRequiresUpdate = true` so the world-map screenshot gets regenerated, and — if the caller asked for it (`updateWorldmap = true`) — immediately calls `WorldMapController.updateWorldMap` and fires `mapLayoutListeners.onMapTilesChanged(map, tileMap)`.

Requirements are the same `Requirement`/`Requirement.RequirementType` objects used by the conversation/quest system — see [quests.md](./quests.md) for how a `Requirement` is evaluated and what fulfilling one can trigger. `ReplaceableMapSection` does not know *why* its condition became true; it is purely a "is this satisfied, and if so which tiles to swap in" mechanism, driven from outside by whatever quest state or script effect flips the underlying flag.

## How other systems hook in

- **`MapLayoutListener`** ([MapLayoutListener.java](../app/src/main/java/com/gpl/rpg/AndorsTrail/controller/listeners/MapLayoutListener.java)) is the extension point for map-visual state changes: `onLootBagCreated`/`onLootBagRemoved` (ground loot appearing/disappearing — item system, see items-equipment.md) and `onMapTilesChanged` (fired whenever `applyCurrentMapReplacements` actually changes something and world-map update was requested) — this is what lets UI/rendering layers know the current map's tiles need to be redrawn after a replacement.
- **Movement & pathfinding** ([movement-pathfinding.md](./movement-pathfinding.md)): `LayeredTileMap.isWalkable`/`PredefinedMap.isWalkable` are the ground truth that `PathFinder` (constructed per-`PredefinedMap`) and monster movement consult; `PredefinedMap.isWalkable(CoordRect, boolean ignoreAreas)` additionally treats active `newmap`/`keyarea`/`rest` event objects as blocking unless `ignoreAreas` is set, and `isWalkable(CoordRect, Monster)` delegates to `MonsterMovementController.monsterCanMoveTo`.
- **Monsters/spawning** ([monsters.md](./monsters.md)): `MonsterSpawnArea` is parsed alongside other map objects (from `spawn`-typed TMX objects) but owned/driven by `MonsterSpawnController`, not by `MapController`; `PredefinedMap.monsters` holds the live monster list per map, and `MapController.handleMapEvent`'s `newmap` case explicitly hands off any monster with a non-null `travelDestination` to `world.monsters`' travelling-monster pool before the player transitions, so a monster mid-journey between maps survives the player's own map change. `TravelDestinationArea.onMonsterArrived` is the landing hook for such a monster, optionally running an `arrivalScript`.
- **Quests & conversations** ([quests.md](./quests.md), [conversations.md](./conversations.md)): `sign`, `script`, and `keyarea` map objects all ultimately call into `ConversationController` — `MapController.runScriptInArea` drives the shared `mapScriptExecutor` (a `ConversationController.ConversationStatemachine`) to `proceedToPhrase`, and `canEnterKeyArea` checks/fulfills a `Requirement` before allowing entry. `ReplaceableMapSection.requirement` and `TravelDestinationArea.arrivalScript` are the same `Requirement`/phrase-ID mechanisms. `MapController.prepareScriptsOnCurrentMap` (called on every map transition) rebuilds `mapScriptExecutor` and wires it (plus the `ControllerContext`) into every `TravelDestinationArea` on the new current map so arrival scripts can run.
- **Save/load** (see save-load.md): `PredefinedMap`/`MapCollection` implement their own `readFromParcel`/`writeToParcel`/`addToChecksum`, with `PredefinedMap.shouldSaveMapData`/`MapCollection.shouldSaveMap` deciding whether a given map's per-map state (spawn/destination area state, monsters, active object groups, ground loot, color filter, visit time) is worth persisting at all — unvisited, untouched maps are skipped to keep savegames small.

## Gotchas / non-obvious behavior worth knowing

- **The "world map" is not a real map.** It is a static HTML page built from per-map PNG screenshots (`WorldMapController`). There is no runtime data structure representing the whole continent as one grid — `WorldMapSegmentMap.worldPosition` only exists to place a map's screenshot inside its segment's HTML layout, and nothing in this codebase lets the player click the world map to travel directly.
- **World-map screenshots are cached per layout hash.** Once a map has been `visited`, its screenshot filename includes `lastSeenLayoutHash` (`WorldMapController.getFileForMap`/`fileForMapExists`). Applying a `ReplaceableMapSection` changes the map's layout hash (`MapController.applyReplacements` updates `map.lastSeenLayoutHash` when it differs from `tileMap.getCurrentLayoutHash()`), which means a map that changes layout via quest progress ends up with *multiple* cached PNGs on disk over a playthrough (one per layout state ever seen), not one file that gets overwritten.
- **Applying one `ReplaceableMapSection` can un-apply another.** If two replacement areas overlap and the later one is applied after the earlier one, the earlier replacement's `isApplied` flag is reset to `false` so it gets re-evaluated — see step 2 above. Order of evaluation (array order in `LayeredTileMap.replacements`, itself TMX-object-group order) therefore matters for overlapping replacements.
- **A `newmap` transition can silently fail with only a log line.** `MovementController.placePlayerAt` returns early (leaving the player where they were) if the destination map name doesn't resolve, if the named place isn't found on that map, or if the place exists but `isActive == false` — all three cases only call `L.log(...)`, there is no player-facing error.
- **`keyarea` blocks movement by other means, not by refusing the map event.** `MapObject.MapObjectType.keyarea` areas are excluded from walkability in `PredefinedMap.isWalkable(area, ignoreAreas=false)` — the "gate" is enforced by pathfinding/movement never allowing the player onto that tile in the first place, with `MapController.canEnterKeyArea` as the actual requirement check/script trigger for scripted key interactions (e.g. a locked-door dialogue), not a blanket movement block by itself.
- **Map object activation groups have a subtlety in `getActiveEventObjectsAt`.** The method only filters on `o.isActive`; the `activeMapObjectGroups.contains(o.group)` check is present in the code but commented out (`//if (!activeMapObjectGroups.contains(o.group)) continue;`), meaning group membership is enforced solely through keeping `MapObject.isActive` in sync (via `activateMapObjectGroup`/`deactivateMapObjectGroup`/`activateMapObjects`) rather than being re-checked at query time.
- **Only `script`-type map events fire during combat.** `MapController.shouldHandleMapEvent` explicitly suppresses every other `MapObjectType` (signs, newmap exits, rest, key areas) while `world.model.uiSelections.isInCombat` is true.
- **`TravelDestinationArea`'s multi-step travel plan is unimplemented.** `executeNextStep()` is a stub ("TODO once implemented... execute steps like 'stay 10', 'goto destArea2'"); only the immediate arrival (`onMonsterArrived`, running `arrivalScript`) is functional today.
- **The TMX tile size is effectively hard-coded to 32px.** `TMXMapFileParser.TILESIZE = 32` is used both to read the map (ignoring the TMX file's own declared size beyond a validation warning) and to convert TMX object pixel coordinates to tile coordinates — a TMX file authored at a different tile size will silently misplace every object's computed grid position.
- **Layer names are matched case-insensitively by convention, not by TMX structure.** `base`/`ground`/`objects`/`above`/`top`/`walkable` are plain string keys (`LAYERNAME_*` constants) looked up in a `HashMap<String, TMXLayer>` built from the raw layer names lower-cased; a `replace` object's per-layer properties can point at an entirely different, arbitrarily-named layer elsewhere in the same TMX file to source its replacement tiles/walkability from.
